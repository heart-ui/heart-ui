# P1-15 `add` and the lock file

## Why

**Request (verbatim):** P1-15 `add` and the lock file (tasks/phase-1.md): `add` with recursive dependency resolution, file writes, npm dependency install, `--overwrite`, and lock file updates. Accept: adding `dialog` also installs `button` and `utils` once each; a second `add` of the same item changes nothing; hashes match files. Unattended run: decisions delegated to the agent.

The task is [tasks/phase-1.md, P1-15](../../../tasks/phase-1.md#p1-15-add-and-the-lock-file). The behaviour is in [registry.md](../../registry.md#commands) (`add`) and [registry.md, Lock file](../../registry.md#lock-file): `add` resolves `registryDependencies` recursively, rewrites import aliases, writes files, installs npm `dependencies` with the project's package manager, updates `heart-ui.lock.json`, and refuses to overwrite an existing file unless `--overwrite`. The lock hash is of the file as written, after alias rewriting. `update` (later) reads the lock to tell an untouched file from an edited one.

**The user's words:** "auto start next item when the current item done, working unattended until 8:00AM tomorrow" (2026-11-18).

## Decisions

| Decision | Ruled out | Why |
|---|---|---|
| Dependencies resolve depth first, each item once, dependencies before dependents; an unscoped dependency resolves in the registry of the item that names it | Unscoped always meaning `@heart-ui` | A third-party item's own helpers live in its own registry. Logged in docs/questions.md. |
| Items you name are written (and, with `--overwrite`, replace your files). An item pulled in as a dependency is written only when its files are missing or identical; when you have changed it, your files are kept, it stays out of the lock, and the output says so | Refusing `add dialog` because you edited `button` | Editing copied source is the point of the library; `update` is the tool for bringing a changed item up to date. |
| A file whose content already equals what `add` would write is not rewritten; an item whose files all match is recorded in the lock without a write | Rewriting identical files | "A second `add` of the same item changes nothing", and `init`'s helpers enter the lock the first time `add` needs them. |
| Destinations: a file under `registry/ui/`, `registry/lib/`, `registry/blocks/` or `registry/layouts/` goes under the matching alias's folder; a file with `target` goes under the project root (`~/` is the root); anything else is refused | Guessing from `type` | Heart UI's own items all use these paths; a guess could write somewhere surprising. |
| Lock entries are keyed by item name (`button`) for `@heart-ui` and by `@scope/name` otherwise, with `registry`, `version` (`meta.version`, or `null`) and `files` (path relative to the root → `sha256-<base64>`) | Hex digests | registry.md's example shows the `sha256-` prefix used by Subresource Integrity, which is base64. |
| Only `registry:ui`, `registry:lib` and `registry:block` items can be added | Themes and other types | registry.md lists those kinds for components, helpers, blocks and layouts; themes go through `heart-ui theme`. |
| The install and write pipeline moves out of `init` into shared modules (`install.ts`, `write.ts`), so `init` and `add` share one copy | Two copies | P1-14's review ticket C11. |

**Proposals not asked for:** None.

## Acceptance criteria

- **AC-001** Given a project set up by `init`, when `heart-ui add dialog` runs, then `dialog` and `button` are written under the `ui` alias folder, `utils` and `icon` are kept as `init` wrote them, each item is fetched once, and the lock lists `dialog`, `button`, `utils` and `icon`.
- **AC-002** Given `dialog` was added, when `add dialog` runs again, then no file, lock entry or package changes, and the output says it is up to date.
- **AC-003** Given an `add`, then every lock hash is the `sha256-` base64 digest of the file as written, and each entry holds the item's registry and version.
- **AC-004** Given aliases other than the defaults in `heart-ui.json`, then files go to those aliases' folders and their imports are rewritten to them.
- **AC-005** Given a named item's file already exists with other content, then `add` exits 1 naming it and suggesting `--overwrite`, and writes nothing; with `--overwrite` it replaces the file and updates the lock.
- **AC-006** Given a dependency whose files you changed, when `add` pulls it in, then your files are kept, it is not locked, and the output names it.
- **AC-007** Given the items' npm dependencies, then those not declared at the same major are installed once with the project's package manager, pinned exactly; a failed install exits 1 with the command to run; a dependency that is not an exact npm spec fails before anything is written.
- **AC-008** Given a mistake, then `add` with no item exits 2; a missing `heart-ui.json` says to run `init`; an unknown item, an item of another type, a file outside the known folders and a malformed lock file each exit 1 with one line naming it, and nothing is written.
- **AC-009** Given `@acme/data-grid` from a third-party registry, then it is fetched from that registry's template, its unscoped dependencies resolve in `@acme`, and its lock entry is keyed `@acme/data-grid` with registry `@acme`.
- **AC-010** Given a write fails partway, then the files written so far are removed or restored and the lock is unchanged.
- **AC-011** Given items that depend on each other in a cycle, then each is fetched and written once.

## Must never break

- `add` never replaces a file you have without `--overwrite`, and never touches a dependency you changed.
- A failed `add` leaves files and the lock as they were.
- Nothing from a registry reaches a shell or a path outside the project unchecked.
- `init` keeps every behaviour P1-14 tested.

## Failure modes

- Untrusted input: items, paths and dependency specs from any registry → AC-007, AC-008, and P1-13's item checks.
- A crash or failure mid-write → AC-010; the lock is written last.
- Persisted data: a malformed or hand-edited lock file → AC-008.

## Out of scope

- `diff` and `update` (they read the lock this writes).
- Removing items.
- Registry dependencies given as URLs (shadcn allows them; registry.md names items by name).
