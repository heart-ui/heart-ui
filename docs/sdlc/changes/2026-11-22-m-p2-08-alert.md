# P2-08 Alert

## Why

**Request (verbatim):** P2-08 alert (tasks/phase-2.md, Tier 2 components)

Task [P2-08](../../../tasks/phase-2.md#tier-2-components), Recipe C: `alert`. Catalog row: built on nothing, parts Title and Description, "`variant`: info, success, warning, danger. Role `alert` for danger, `status` otherwise." The spec is [registry/ui/alert/alert.md](../../../registry/ui/alert/alert.md). Pages, forms and the `error-state` block (P2-44) need a message that stays in the page, unlike a `toast`.

## Decisions

| Decision | Ruled out | Why |
|---|---|---|
| Parts `Alert` (`variant`, `class`), `AlertTitle`, `AlertDescription` (`class`); `info` by default | A `neutral` variant; a `title` prop | The catalog lists four variants; `info` is the mildest. Text enters by the parts' slots, as in `card`. |
| Each variant is its `-subtle` background and text pair with a border in the status colour, as `toast` does | New alert tokens | Same message colours across items, with text pairs that are already contrast-checked. |
| A leading icon per variant: `info`, `success`, `warning`, `error`; decorative | Colour alone; an icon slot | Status shouldn't rest on colour alone, and the title names it in words. A slot is a second way to do one thing. |
| Add `success` (`fluent:checkmark-circle-20-regular`) to the icon set and bump the `icon` item to 0.3.0 | Reusing `check` | It matches the other circled status icons. 0.2.0 is published, and a published version can't change (registry.md). |
| Title and description are `div`s | A heading element | The heading level depends on the page; a `div` never breaks the outline. |

## Acceptance criteria

- **AC-001** Spec, Props: each variant has its `-subtle` background and text pair, a border in its status colour, and its icon (`info`, `success`, `warning`, `error`); `info` is the default.
- **AC-002** Spec, Accessibility: `danger` has `role="alert"`; every other variant has `role="status"`; the icon is `aria-hidden`.
- **AC-003** Spec, Slots: `AlertTitle` and `AlertDescription` render their slots beside the icon, the title in medium weight.
- **AC-004** Spec, Props: other attributes fall through to each part's element, and `class` merges last.
- **AC-005** Definition of done 3: axe reports no violations in the demo, light and dark.
- **AC-006** Definition of done 1, 4–6 and the docs page: the registry build includes `alert` and the new icon, and the docs site builds its page and demo.

## Review

Code review fired (`## Public Surface` adds `alertVariants`); low risk, so it ran without asking. Two rounds of `code-review high --max-findings all`, rated by the agent; no high findings.

**Changed from the plan above.** `success` uses the existing `check` icon, not a new `success` icon. The icon set and the `icon` item stay at 0.2.0, so the Decisions row about the new icon, AC-001's `success` icon, AC-006's "new icon" and Task 1's icon files no longer apply. Why (F1): a project that already has `icon` 0.2.0 keeps it on `heart-ui add alert`, since `add` skips a dependency whose files match the lock and `update` isn't built yet. A new icon would have crashed every `success` alert there.
