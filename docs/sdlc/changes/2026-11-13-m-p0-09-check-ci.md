# P0-09 Check command and CI

## Why

**Request (verbatim):** "continue" (the maintainer delegated decisions: "you decide for me, i will look at the final product only"; next ready task: P0-09).

Task [P0-09](../../../tasks/phase-0.md#p0-09-check-command-and-ci): one command that runs every gate in [conventions.md §Checks](../../conventions.md#checks) in order, a per-item version of it, CI that runs it on pull requests, and the Changesets setup that releases need.

## Decisions

| Decision | Ruled out | Why |
|---|---|---|
| `scripts/check.ts` runs the steps in conventions order (`lint`, `typecheck`, `test:unit`, `test:browser`, `test:visual`, `test:ssr`, `registry:build`), stops at the first failure and names it. `--dry-run` prints the plan. `pnpm check` is `node scripts/check.ts`; `pnpm check:item <name>` adds `--item`. | a chain of `&&` scripts | One place decides the order and the item scoping, and a test can read the plan. |
| `check:item` scoping per step: <ul><li>`lint`: ESLint and Prettier on the item folder.</li><li>`typecheck`: `vue-tsc` on a temporary tsconfig that extends `registry/tsconfig.json` and includes only the item folder.</li><li>`test:unit`: Vitest filtered to the item folder.</li><li>`test:browser`: the item's demo (through Vitest `provide`) and the item's own browser test.</li><li>`test:visual`: `--grep` on the item's title.</li><li>`test:ssr`: the item's demo.</li><li>`registry:build`: builds the whole registry into a temporary folder and checks the item's `r/<name>.json` exists, or reports it as a fixture.</li></ul> Steps with no tests for the item pass and say so. | build only the item | `registryDependencies` need the other items to validate. The placeholder is a fixture with no `item.json`. |
| `.github/workflows/check.yml`: on pull requests and pushes to main, Ubuntu, Node 22, pnpm through `pnpm/action-setup`. It runs `pnpm install --frozen-lockfile`, `pnpm test:install --with-deps`, `pnpm check`, then `pnpm test:harness`. Actions are pinned to their current major tags (checkout v7, setup-node v7, pnpm/action-setup v6). | Docker-in-Docker | GitHub's Ubuntu runners have Docker, so `test:visual` runs the same container as locally. The harness proves on Linux that every check still fails on its seeded regression. |
| "Blocks merge on failure" needs a branch-protection rule on the GitHub repo, which doesn't exist yet (no remote). | — | A repository setting, not a file. Listed for the maintainer. |
| Changesets 3.0.3: `.changeset/config.json` is the CLI's own default (`defaultWrittenConfig` in `@changesets/config` 4.0.1), with `access: "public"`. The README is `changeset init`'s. | `access: "restricted"` (the default) | Open-source packages published to npm with provenance (conventions, Toolchain). The interactive `init` asks only about a GitHub changelog, and there's no remote yet. |

**Proposals not asked for:** None

## Acceptance criteria

- **AC-001** conventions §Checks: `pnpm check` runs `lint`, `typecheck`, `test:unit`, `test:browser`, `test:visual`, `test:ssr`, `registry:build` in that order, each as its standalone script, and stops at the first failure, naming it.
- **AC-002** Task Accept: `pnpm check:item placeholder` runs every step, each scoped to that item only, and passes.
- **AC-003** `check:item` with a name that isn't an item fails, naming it, before running any step.
- **AC-004** Task Deliver: a GitHub Actions workflow runs `pnpm check` on pull requests, with Chromium and Docker available.
- **AC-005** Task Deliver: Changesets is configured; `changeset status` reads the config.

| AC-005 | tests/check.test.ts › changesets | `pnpm vitest run tests/check.test.ts -t "changesets"` |

## Must never break

- Each step stays runnable on its own (`pnpm lint`, `pnpm test:visual`, ...).

## Out of scope

- Branch protection on GitHub (maintainer, once the repo exists); publishing workflows (release task); P0-03's F8 (lint in CI) is closed by this workflow.
