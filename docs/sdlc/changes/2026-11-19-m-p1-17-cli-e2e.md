# P1-17 CLI end-to-end test

## Why

**Request (verbatim):** P1-17 CLI end-to-end test (tasks/phase-1.md): `test:cli-e2e`. It copies committed minimal Nuxt and Vite templates to a temp folder, serves the local registry build, runs `init` and `add` for every Tier 1 item, builds the app, and renders a page that uses each component. Accept: passes for both templates; added to `pnpm check`. Unattended run: decisions delegated to the agent.

The task is [tasks/phase-1.md, P1-17](../../../tasks/phase-1.md#p1-17-cli-end-to-end-test). It proves the alpha's promise ([spec.md, Release stages](../../spec.md)): a Nuxt app and a Vite app install and render every Tier 1 component from the CLI. P1-14 left the way to point `init` at another registry to this task.

**The user's words:** "auto start next item when the current item done, working unattended until 8:00AM tomorrow" (2026-11-18).

## Decisions

| Decision | Ruled out | Why |
|---|---|---|
| `init --registry <url>` sets the `@heart-ui` item URL template in `heart-ui.json` | An environment variable, or a test-only hook | A mirror or a self-hosted registry is a real use; the test drives the built CLI as a user would. |
| Packages install for real with pnpm, `prefer-offline`: from the store when it has them, fetching only missing metadata | An offline install (pnpm has no cached metadata after a frozen workspace install) or skipping installs | The install is part of what `init` and `add` do; the store keeps it to seconds. |
| The page renders each Tier 1 item's own demo, copied next to the installed item | Hand-written usage per component | The demos are the items' maintained examples, and they import the way a user's code does (`@/components/ui/...`, `.`). |
| The app is opened in Chromium (Vite preview; Nuxt's built server, so SSR runs too) and each item's section must render with no page or console error, and `--h-primary` must be set | Checking HTML only | Rendering in a browser is the accept line; console errors catch hydration and runtime failures. |
| `test:cli-e2e` runs through its own Vitest config, is excluded from `test:unit`, and is the last step of `pnpm check`; `check:item` skips it with a note | Part of `test:unit` | It takes minutes and needs the network for metadata; one item's check doesn't need whole apps. |

**Proposals not asked for:** None.

## Acceptance criteria

- **AC-001** Given the committed Vite template, when the test copies it, installs it, runs the built CLI's `init --yes --registry <local>` and `add` with every Tier 1 item, builds it and opens it in Chromium, then every item's demo renders with no page or console error and the theme's `--h-primary` is set.
- **AC-002** Given the committed Nuxt template, the same steps pass, with Nuxt's built server rendering the page.
- **AC-003** Given `init --registry <url>`, then `heart-ui.json` holds that template for `@heart-ui` and the helpers come from it; a URL the config refuses (plain http to another host) exits 1 before anything is fetched or written.
- **AC-004** Given `pnpm check`, then `test:cli-e2e` runs as its last step; `check:item` lists it as skipped.

## Must never break

- `pnpm test` (the unit suite) stays fast: the end-to-end test is not part of it.
- `init` keeps every P1-14 behaviour without `--registry`.

## Failure modes

- Network: pnpm fetches missing package metadata → a failure names the command and its output.
- Leftovers: temp folders, the registry server, preview servers and the browser are closed even when a step fails.

## Out of scope

- Publishing the registry (P1-18) and installing from the published CLI (the alpha gate, P1-21).
- Visual or accessibility checks of the rendered page (the playgrounds own those).
