# P1-14 `init`

## Why

**Request (verbatim):** P1-14 `init` (tasks/phase-1.md): the `init` command per the command table. Fails with a clear message when Vue, Nuxt, Node, or Tailwind is below the minimum. Accept: on a fixture project, `init --yes` produces a project that builds and resolves `bg-primary`. Unattended run: decisions delegated to the agent.

The task is [tasks/phase-1.md, P1-14](../../../tasks/phase-1.md#p1-14-init). The command table row in [registry.md](../../registry.md#commands) says `init` detects Nuxt or Vite, checks Tailwind v4 and the minimum versions, and writes `heart-ui.json`, `tokens.css`, `theme.css`, the `utils` and `icon` helpers, and the agent rule files ([agent-support.md](../../agent-support.md#project-rule-files)). Flags: `--theme <preset>`, `--yes`. The minimum versions are in the [constitution](../constitution.md#technology-constraints): Vue 3.5, Nuxt 4, Node 22, Tailwind CSS v4. `init` is the first command a user runs; the spec's success measure is "`init` to a themed first screen" in under 10 minutes.

**The user's words:** "auto start next item when the current item done, working unattended until 8:00AM tomorrow" (2026-11-18).

## Decisions

| Decision | Ruled out | Why |
|---|---|---|
| `tokens.css` comes from `generateTheme(knobs)` of `@heart-ui/theme`, and `theme.css` is that package's static `theme.css`; the CLI depends on `@heart-ui/theme` | Fetching them from the registry | The registry build skips `registry/themes` and the theme command (registry.md) runs `generateTheme`, so the CLI needs the package anyway. One source for both files. |
| Presets are the knob files in `registry/themes/`, bundled into the CLI; `--theme` defaults to `default`; an unknown name fails listing the presets | Fetching knob files | They are not hosted (the build skips them); bundling keeps `init` working offline for the theme. |
| The theme files go to `app/assets/css/` (Nuxt) or `src/assets/css/` (Vite) as `theme.css` and `tokens.css`; `heart-ui.json` `css` holds the `theme.css` path | `heart-ui.css`, as registry.md's config example names it | The command table names `theme.css` and `tokens.css`; `theme.css` imports `./tokens.css`, so they sit together. Logged in docs/questions.md. |
| The project's CSS entry is wired in: when exactly one `.css` file under `src/` or `app/` has the line `@import "tailwindcss";`, that line becomes `@import "<relative path>/theme.css";` (which imports Tailwind itself); otherwise nothing is edited and the output names the file to import | Editing `main.ts` or `nuxt.config` | A Tailwind v4 project already imports Tailwind from one CSS file; swapping that line is the smallest edit that makes `bg-primary` resolve. Code files are left alone. |
| Default aliases are registry.md's (`@/components/ui`, `@/components/blocks`, `@/layouts`, `@/lib`); `init` fails when the project has no `@` alias, naming the `tsconfig.json` entry to add | Writing the alias into `tsconfig.json` and `vite.config` | Editing build config is out of the task; a clear message is enough, and Nuxt has `@` by default. |
| The helpers' npm dependencies not already in `package.json` are installed with the detected package manager, pinned exactly (`--save-exact`, `--exact`), run without a shell; each dependency must look like an npm package spec | A shell command line | Registry items are untrusted (P1-13 R2-4); no shell means no injection, and the spec check rejects anything else. |
| `init` refuses when `heart-ui.json` or any file it would write already exists, before writing anything | Overwriting, or an `--overwrite` flag | The command table gives `init` no overwrite flag; a re-run must not clobber edited helpers. |
| Without `--yes`, `init` lists what it will write and asks to continue when stdin is a terminal; otherwise it stops and says to pass `--yes` (exit 2) | Prompting for each choice | One confirmation covers the only decision left; the theme comes from `--theme`. |
| The default `@heart-ui` registry URL is one constant, `https://registry.heart-ui.dev/r/{name}.json`, until P1-18 picks the host | Leaving it out | `heart-ui.json` needs a template; logged in docs/questions.md for the hosting task. |
| The build test runs a real Vite build of the initialised fixture, inside `packages/cli/node_modules/` so it resolves `vite`, `@tailwindcss/vite` and `tailwindcss`, added to the CLI's devDependencies at the playground's pinned versions | Spawning `pnpm install` in a temp project | No network in tests; the accept line asks for a build. |

**Proposals not asked for:** None.

## Acceptance criteria

- **AC-001** Given a Vite project with Tailwind 4, when `heart-ui init --yes` runs, then it writes `heart-ui.json` (framework, css path, the default aliases, `fluent`, the `@heart-ui` registry), `src/assets/css/theme.css` (the theme package's file), `src/assets/css/tokens.css` (the default preset), the `utils` and `icon` helpers under `src/lib/` with imports rewritten to the project's aliases, and installs the helpers' missing npm dependencies once with the project's package manager.
- **AC-002** Given that initialised Vite project, when it is built with Vite, then the build succeeds and the CSS holds `.bg-primary{background-color:var(--h-primary)}` and the `--h-primary` token.
- **AC-003** Given a Nuxt 4 project, when `init --yes` runs, then the theme files go to `app/assets/css/`, `heart-ui.json` says `nuxt`, and the helpers go under `app/lib/`.
- **AC-004** Given a project below a minimum (Node under 22, Vue under 3.5, Nuxt under 4, Tailwind under 4 or missing, Vue missing in a Vite project, neither Nuxt nor Vite), when `init` runs, then it exits 1 with one line naming what was found and what is needed, and writes nothing.
- **AC-005** Given `--theme <preset>`, then `tokens.css` is that preset's; an unknown preset exits 1 listing the presets and writes nothing.
- **AC-006** Given `heart-ui.json` or any file `init` would write already exists, then `init` exits 1 naming it and writes nothing.
- **AC-007** Given no `--yes`, when stdin is a terminal, then `init` lists the files and asks to continue (no writes nothing, exit 1); when it is not a terminal, it exits 2 telling the user to pass `--yes`.
- **AC-008** Given `init` runs, then `AGENTS.md` (under 40 lines) names where components, blocks, layouts and helpers live, the screen workflow, `heart-ui list` and the MCP `search_items` tool, the hard rules and `heart-ui audit <files>`; an existing `AGENTS.md` gets the block appended once, and an existing `CLAUDE.md` gets one pointer line to `AGENTS.md`.
- **AC-009** Given exactly one CSS file under `src/` or `app/` imports `tailwindcss`, then that import becomes an import of `theme.css`; with none or several, no CSS is edited and the output names `theme.css` as the file to import.
- **AC-010** Given a project with no `@` alias, then `init` exits 1 naming the `paths` entry to add, and writes nothing.
- **AC-011** Given dependencies, then those already in `package.json` are skipped, the install command pins exactly for each package manager and runs without a shell, a failed install exits 1 with the command to run by hand, and a dependency that is not an npm package spec fails before anything is written.

## Must never break

- `init` never overwrites a file the user has, and a refused or failed check writes nothing.
- Nothing from a registry reaches a shell; package names are checked and passed as arguments.
- Every failure is one line with exit 1 (2 for usage), never a stack or raw system text.

## Failure modes

- Untrusted input: dependency names and file paths from the registry → AC-011, and P1-13's item checks.
- Partial failure: the install fails after the files are written → AC-011 (the message gives the command to finish).
- A crash mid-write: every file is written with the atomic write from P1-13.

## Out of scope

- `add`, the lock file and recursive registry dependencies (P1-15); `init` writes no lock file (registry.md: only `add` and `update` do).
- Editing `vite.config`, `nuxt.config`, `main.ts` or `tsconfig.json`.
- A flag or variable for another registry URL (P1-17 adds what the end-to-end test needs).
- The MCP server (Phase 2); `AGENTS.md` names its tool as the docs say.

- **Fixed:**
  - S1: a failed install printed registry text as a command to paste. Dependencies must now be exact `name@x.y.z` specs, which admit no shell or cmd.exe metacharacters.
  - S2 and R2-S2: control characters. Registry paths holding them are invalid items, and refused values are printed with C0 and C1 escaped.
  - S3, C1, R2C1, R2C3, R2C4: write order and rollback.
    - Any entry at a target (a folder, a dangling link) is refused.
    - New files are created with `link`, so nothing is replaced.
    - `heart-ui.json` is written last.
    - A failure removes created files and folders and restores edits.
  - S4, C2, R2-S1: links. Edits go to the link target and keep its mode, a `CLAUDE.md` linked to `AGENTS.md` gets no pointer, and an agent file linking outside the project is refused.
  - R2-S5 / R2C2: edits re-read their target and stop if it changed.
  - C3: Windows starts the package manager through a shell; the strict specs keep that safe.
  - C4, R2C5: caret, `>=`, `3.x`, `~3` and `3` ranges are open, so `^3.4.0` is not refused.
  - C5: Ctrl+C and Ctrl+D at the prompt mean no.
  - C6, R2C6: a helper dependency declared at another major is installed; `catalog:` and `workspace:` ranges are kept.
  - C7: the confirmation lists the packages.
  - C8, C9, R2C11: CSS entry matching. CRLF and `$` are safe, and block comments are ignored.
  - R2C8: the `--yes` check runs before any I/O.
  - R2C10: pnpm gets `-w` at a workspace root.
  - C16: the config example now says `theme.css`.
